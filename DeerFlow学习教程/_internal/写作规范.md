## 1. 我们在做什么

- 仓库：`c:\code\cursor\deer flow\deer-flow`（字节跳动 DeerFlow 2.x，版本 `2.2.0-dev`，写作基线提交 `8d994cc1`，分支 `main`）。
- 产出：一套**中文 Markdown 学习教程**，全部放在仓库根目录的 `DeerFlow学习教程/` 文件夹里（子目录见第 11 节）。
- 读者画像：**刚接触 DeerFlow**、有一点 Python / Web 基础、但对 LangChain / LangGraph / Agent 工程不熟的开发者。他的最终目标是**成为这个开源项目的 committer**。
  所以每一章既要把"它是什么、为什么这样设计"讲明白（大白话、多例子），也要讲清楚"改这一块代码要注意什么、怎么测试、怎么提交"。
- 要求：**系统、细致、从入门到精通**；源码挑重点精读；**尽量不出错**；多用大白话、多举例子。

## 2. 文风：大白话，但不糊弄

1. **先类比，再定义，再落到源码**。每个新概念按这个顺序讲：
   ① 一句生活化的比喻 → ② 它在技术上到底是什么 → ③ 在 DeerFlow 里它长什么样、在哪个文件。
2. 用"你"称呼读者，口吻像一个耐心的学长在带你读源码；不要居高临下，不要堆黑话。第一次出现的英文术语要给中文解释，并在括号里保留英文，例如"检查点（checkpoint）"。
3. **每个重要机制都要有一个"具体场景走一遍"**：比如"用户发了一句 `帮我查一下今天的天气`，这时中间件 A 做了什么、工具 B 被谁调用……"。
4. 解释"**为什么这样设计**"比解释"是什么"更重要：这个设计解决了什么问题？不这样做会怎样？有什么取舍？（源码注释和 AGENTS.md 里常有线索。）
5. 禁止空话套话（"非常强大""灵活可扩展"这类没有信息量的词）；禁止只罗列 API 不解释；禁止把英文注释机械翻译一遍就当讲解。
6. 难点要拆开讲：先讲最简单的情形，再讲边界情况；必要时用"如果……会怎样？"的问答小节。

**示范段落（照这个语气写）**：

> 想象你开了一家外卖店。**Gateway** 就是前台：所有订单（HTTP 请求）先到它这儿，它负责登记、验证身份，然后把单子交给后厨（Agent）。
> **Nginx** 则是门口的导引员——顾客只需要记住一个门牌号（端口 `2026`），导引员根据订单类型把人领到前台还是领到大堂（前端页面）。
> 这样设计的好处是：浏览器只面对"一个域名一个端口"，不会遇到跨域（CORS）这种让新手头疼的问题。

- **长度**：除非主题确实很小，每章不少于 **350 行**，目标 **500~900 行**。宁可讲细，不要讲糙。
- **小节编号**用阿拉伯数字（`## 1.`、`### 1.1`），方便口头引用。

## 4. 准确性铁律（最重要！）

1. **所有类名、函数名、配置键、文件路径、命令、端口、环境变量名，都必须从源码里核实后再写**（用 `rg` / Grep / 读文件）。**不确定就不写**；宁可少写一句，也不要编造。
2. **数字必须当场数出来**：中间件个数、路由个数、工具个数、配置项个数……写成"截至提交 `8d994cc1`，共 N 个"。数的方法要写进你的核实笔记里（不必写进文档）。
3. **旧文档可能过期，以源码为准**。已知过期：`backend/docs/middleware-execution-flow.md`（只列了 14 个中间件，实际约 40 个）。发现新的"文档与源码不一致"，请在最终汇报里告诉我。
4. **不要把读文件工具输出的行号前缀（形如 `  123| `）粘进文档**。
5. **不要写死行号**（行号会漂移）。定位源码请用"文件路径 + 函数名/类名"。
6. 讲"版本相关/配置相关"的行为时，要写清前提条件（比如"默认值是 X；在 config.yaml 里把 Y 改成 Z 才会……"），默认值必须核实。
7. **示例代码分两类，必须明确标注**：
   - **源码原文**：逐字复制，只能用 `# ...` / `// ...` 表示省略；**代码块里不要插入中文解释性注释**（解释写在代码块后面的"逐段解释"里；确实想标记行，可在行尾加 `# <-- ①`）。必须在代码块上一行用"来源"引用块标注出处（格式见第 6 节）。
   - **示意代码 / 自己写的示例**：必须在代码块前一行明确写"**示意代码（非源码原文）**"；里面用到的、仓库里并不存在的新名字（如 `my_new_tool`）要追加到 `DeerFlow学习教程/_internal/allow_symbols.txt`。
8. 不要断言你没验证过的"运行时行为"。可以说"从代码看，……"，并指出依据的函数。
9. 对"外部库（LangChain/LangGraph/FastAPI/Next.js 等）"的讲解只讲到"够理解 DeerFlow 为什么这样用"的程度，不要凭记忆写具体版本细节；必要时引用仓库里 `pyproject.toml` / `package.json` 的真实版本约束。

## 5. 源码阅读方法（给 agent 的操作提示）

- 当前环境是 **Windows + PowerShell**。读文件/搜索请用 `Grep`（ripgrep）工具、`Glob` 工具，或在 `Shell` 里用 `rg -n "模式" 路径`。
- 想看某文件的某几行：`Get-Content -LiteralPath <文件> -Encoding UTF8 | Select-Object -Skip 99 -First 60`。
- **编码陷阱（务必注意，已经踩过）**：源码里有很多非 ASCII 字符（破折号 `—`、箭头、中文注释等）。PowerShell 默认输出编码会把它们悄悄显示成别的字符（例如 `—` 被显示成 `-`），**你照着控制台输出抄代码就会抄错一个字符**。所以：每次开 Shell 先执行 `[Console]::OutputEncoding = [Text.Encoding]::UTF8; $OutputEncoding = [Text.Encoding]::UTF8`；复制代码块时，以 `Grep` / `Read` 工具的输出为准（它们不经过控制台编码）。体检脚本会把这种“抄错一个字符”的行报成 `[W]`，必须修正。
- **风格范例**：先浏览 `DeerFlow学习教程/02-全局架构篇/03-一次对话的完整旅程.md` 的前 300 行（它是我亲自写的范例章：结构、语气、"来源"引用块、逐段解释、表格、ASCII 图都照它来）。
- `Read` 工具读 `backend/` 下文件时，可能会把巨量的 `AGENTS.md` 规则文本一并附带，浪费上下文；如果你发现这种情况，改用 Shell 读取。
- 仓库每个重要目录往往有 `AGENTS.md`：那是维护者写给 agent 的"内部笔记"，信息密度很高，**先读它**，再读代码验证；但教程里不要大段照抄，要消化成大白话。
- **只读**：除了你负责的教程文件，**不要修改仓库里任何其它文件**（尤其不要改 `AGENTS.md`、`CLAUDE.md`、源码、配置）。不要运行 `make dev`、`pnpm install`、`uv sync`、`docker`、`pytest` 等重型/有副作用的命令（`git log`、`git show`、`rg`、`ls`、`python -c` 解析之类只读命令随意）。
- 文件很大时（几千行）不要通读，先 `rg -n "^(async )?def |^class "` 看骨架，再挑重点读。

## 6. 源码引用与链接规范

**"来源"引用块（每个源码原文代码块的上一行必须有）**：

```markdown
> 来源：[`backend/app/gateway/services.py`](../../backend/app/gateway/services.py) → `format_sse`
```

- 链接文字用**等宽字体包裹的仓库相对路径**；链接目标是**相对当前 md 文件的路径**。
- 教程文件位于 `DeerFlow学习教程/<篇名>/xx.md`，到仓库根要 `../../`；位于 `DeerFlow学习教程/README.md`，到仓库根要 `../`。
- 行内提到源码文件时，也尽量带链接：`[`app.py`](../../backend/app/gateway/app.py)`；提到函数/类时用行内代码 `` `make_lead_agent` ``，并在附近给出它所在文件的链接。
- 教程内部互链也用相对路径，例如：`[中间件链](./04-中间件链.md)`；跨篇：`[一次对话的完整旅程](../02-全局架构篇/03-一次对话的完整旅程.md)`。
- **每写完一章，必须运行体检脚本**（见第 9 节）并修复所有 `[E]`。

## 7. 排版规范

- 一级标题（`# `）**全文只能有 1 个**；正文从 `## ` 起。中文标点；中英文之间不强制加空格，但全书保持一致（建议加半角空格）。
- 代码块必须标注语言：`python` / `typescript` / `yaml` / `bash` / `powershell` / `json` / `text` / `mermaid` / `toml` / `sql` / `nginx`。
- **图**：优先使用 ```` ```text ```` 的 ASCII 图（任何查看器都能正常显示）。ASCII 图规则：
  - **不要画右侧封口的方框**（中文字符宽度会导致右边框错位）；用"缩进 + 箭头 + 竖线"表示层次与流向，例如：
    ```text
    浏览器
      │  POST /api/langgraph/threads/xxx/runs/stream
      ▼
    Nginx(:2026)  ──改写路径──▶  Gateway(:8001)
    ```
  - 复杂的时序图可以用 ```` ```mermaid ````（`sequenceDiagram` / `flowchart`），但**必须同时附一段文字说明**，且 mermaid 里节点文字含括号、冒号、引号时要加双引号；不要只给 mermaid 不给文字。
- 表格用来做"对照/速查"（字段 | 含义 | 默认值 | 出处）。表格单元格里不要放换行。
- 强调用 **粗体**，路径/标识符/命令用 `行内代码`。
- 提示框统一用引用块 + 粗体前缀：`> **小贴士**：…` / `> **注意**：…` / `> **为什么这样设计**：…`。
- 不要使用 emoji。

## 9. 交付前自检（必做）

写完每一章（或一批章节）后，在仓库根目录运行：

```powershell
python DeerFlow学习教程/_internal/check_docs.py 03-后端核心篇/04-中间件链.md
# 一次检查多个：
python DeerFlow学习教程/_internal/check_docs.py 03-后端核心篇/04-中间件链.md 03-后端核心篇/05-线程状态与检查点.md
```

脚本会检查：

- `[E]` 链接目标不存在 / 行内代码里的仓库路径不存在 / 代码围栏没闭合 / 一级标题数量不对 / 残留行号前缀 —— **必须全部修复**。
- `[W]` 行内标识符在整个仓库里搜不到（疑似杜撰）/ "来源"代码块里有行在源文件里找不到（疑似改写）/ 锚点找不到 —— **逐条处理**：真的写错了就改；确属有意编造的示例名，追加到 `_internal/allow_symbols.txt`（用 `Add-Content -Encoding utf8`，**不要覆盖整个文件**）；"来源"代码块不是原文就改成"示意代码"并去掉"来源"引用。
- `[I]` 含"待核实/TODO"。**交付时不应残留**；实在无法核实的内容，删掉，并在最终汇报里告诉我。

除了脚本，你还要**自己抽检**：挑 5 处最关键的论断（函数做了什么、默认值是多少、调用顺序），回源码再核对一遍。

## 10. 最终汇报格式（给我，不超过 250 字）

1. 写了哪些文件（路径 + 行数）；
2. `check_docs.py` 最终结果（E/W 数量，剩余 W 的原因）；
3. 发现的"文档与源码不一致"/ 过期文档；
4. 你认为其它章节需要注意的事实（比如"这个模块和 X 章有强耦合，X 章应说明…"）；
5. 无法核实而删掉的内容。

**不要在汇报里贴章节正文。**

## 12. 已核实的全局事实（可以直接用，但引用到具体细节时请自己再核对一次）

- 版本：`backend/pyproject.toml` 与 `frontend/package.json` 均为 `2.2.0-dev`；后端 Python `>=3.12`；前端 `packageManager` 为 `pnpm@10.26.2`；基线提交 `8d994cc1`。
- 四个服务：Nginx `:2026`（唯一对外入口）、Gateway `:8001`（FastAPI + 内嵌 LangGraph 兼容运行时）、前端 Next.js `:3000`、可选 Provisioner `:8002`（仅沙箱走 provisioner/K8s 模式时）。
- Nginx 把 `/api/langgraph/*` 改写成 `/api/*` 再转给 Gateway；其余 `/api/*` 直接转给 Gateway；其它请求交给前端。
- 后端分层：`backend/packages/harness/deerflow`（包名 `deerflow`，Harness 层，可独立发布）与 `backend/app`（包名 `app`，App 层）。依赖方向：App 可以 import Harness，**Harness 绝不能 import App**，由 `backend/tests/test_harness_boundary.py` 强制。另有 `backend/packages/extension-api`（包名 `deerflow_extension_api`，扩展公共契约）。
- 主智能体由 `backend/packages/harness/deerflow/agents/lead_agent/agent.py` 里的 `make_lead_agent` / `assemble_lead_agent` 组装，核心是 `langchain.agents.create_agent(...)`。
- 一次对话主干线：`POST /api/langgraph/threads/{id}/runs/stream` → Nginx 改写 → `stream_run`（`app/gateway/routers/thread_runs.py`）→ `start_run`（`app/gateway/services.py`）→ `RunManager.create_or_reject`（`deerflow/runtime/runs/manager.py`）→ `asyncio.create_task(...)` 启动 `run_agent`（`deerflow/runtime/runs/worker.py`）→ `agent.astream(...)` → `StreamBridge.publish`（`deerflow/runtime/stream_bridge/`）→ `sse_consumer` + `format_sse` → 浏览器。
- 并发策略 `multitask_strategy` 实际支持 `reject` / `interrupt` / `rollback`（**不支持 `enqueue`**）。
- 提交信息风格：约定式提交 + PR 号，例如 `fix(search): surface DuckDuckGo search failures instead of reporting an empty result (#6648)`。
- 仓库规则（根 `AGENTS.md`）：后端强制 TDD（测试在 `backend/tests/`）；改动用户可见行为要同步更新 `README.md`，改动开发/架构要同步更新相关 `AGENTS.md`；推送前后端 `make format`、前端 `pnpm check`；不要编辑 `CLAUDE.md`；扩展优先（先评估能否做成扩展，再决定是否改核心）；版本号三处联动（`backend/pyproject.toml`、`frontend/package.json`、`deploy/helm/deer-flow/Chart.yaml`，外加 `backend/uv.lock`），用 `scripts/bump_version.sh` 与 `scripts/verify_versions.sh`。
- 用户本机环境（仅供写"环境准备"章参考）：Windows 10 + PowerShell；本机已有 Python 3.14、Node 25；**没有** `uv`、`pnpm`、`make`、`docker` 在 PATH 里。仓库提供 `scripts/run-with-git-bash.cmd` 等 Windows 辅助脚本。

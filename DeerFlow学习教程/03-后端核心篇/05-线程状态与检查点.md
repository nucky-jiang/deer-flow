# 线程状态与检查点：Agent 的“记事本”和“存档点”

> 你和 Agent 聊了十轮，刷新一下页面它还记得前面说过什么；点“重新生成”它能退回到几分钟前重新来过；网关重启之后，没聊完的会话照样能接着聊。
> 这几件事背后只有两样东西：**线程状态（ThreadState）**和**检查点（checkpoint）**。本章把它们从“是什么”一路讲到“怎么存、怎么合并、怎么回滚、怎么改”。

## 本章你将学到

- **State（状态）、Checkpoint（检查点）、Thread（会话线程）、Run（一次运行）** 四个名词的关系，以及为什么多轮对话、刷新页面、中断恢复都离不开它们。
- `ThreadState` 的全部字段：截至提交 `8d994cc1`，它自己声明了 **18 个字段**，再加上从 LangChain `AgentState` 继承来的 `messages`；每个字段的类型、合并规则、谁写、谁读。
- 为什么状态字段**不能“后写覆盖前写”**：并行工具调用、子智能体回写、中间件被反复执行，各自会怎样把状态写坏；DeerFlow 用哪些 **reducer（合并函数）** 化解，以及条数上限（cap）、幂等去重、`Overwrite` 绕行这些细节。
- 检查点的两种存档方式 **`full`（整份）与 `delta`（增量）**：差别、取舍、为什么“进程内冻结、改了必须重启”，以及 `CheckpointStateAccessor` 为什么是读写检查点的唯一入口。
- checkpointer 后端（内存 / SQLite / Postgres）与 `CachedHistorySaver` 历史缓存。
- “取消并回滚”“重新生成”“编辑重发”“分支”是怎样建立在检查点之上的。
- 给未来 committer 的清单：新增一个状态字段要改哪几处、跑哪些测试、有哪些红线。

## 先用一句大白话讲清楚

想象你在玩一款单机游戏。

| 游戏里的东西 | 在 DeerFlow 里对应 | 一句话 |
| --- | --- | --- |
| 角色面板（血量、背包、任务栏） | **State（线程状态）**，即 `ThreadState` | “此刻世界长什么样”：聊天记录、待办清单、产出的文件…… |
| 一份存档 | **Checkpoint（检查点）** | 某一刻面板的完整快照，还记着“我的上一份存档是哪个” |
| 存档文件夹（一个角色一个） | **Thread（会话线程）**，即 `thread_id` | 同一个 `thread_id` 下的所有检查点串成一条时间线 |
| 打一关 | **Run（一次运行）** | 用户发一条消息触发的一次完整 Agent 执行 |
| 存档管理员 | **Checkpointer（检查点存储后端）** | 决定存档放在内存、SQLite 文件还是 Postgres 里 |

所以一句话：**State 是“面板”，Checkpoint 是“面板的存档”，Thread 是“存档文件夹”，Run 是“这一关的游戏过程”。** Agent 每走一步，面板上的数字就变一次，LangGraph 顺手存一份档；下次你回来（哪怕是服务器重启之后），从最新的存档读出面板，接着玩。

本章在全书里的位置：[一次对话的完整旅程](../02-全局架构篇/03-一次对话的完整旅程.md) 的第 8 节讲了 `run_agent` 怎样启动图，第 15 节讲了 `checkpointer`、`store` 这些单例怎样在网关启动时创建；这两处都把“读档 / 存档”一笔带过了，本章把它拆开讲透。SQL 表、Alembic 迁移、Repository 这类“应用数据”的存储属于姊妹章 [持久化与数据库](./12-持久化与数据库.md)，这里只在交界处提到。

## 1. 四个名词：Thread、Run、State、Checkpoint

### 1.1 一张图看清它们的关系

下面这张图是**示意**（具体一个 Run 写几个检查点，取决于图里有多少个节点、模型调了几次工具）：

```text
Thread T1（thread_id = T1，一次连续对话）
  │
  ├── Run r1（用户发第 1 条消息）
  │     ├── 检查点 c1   用户输入写入之后             metadata.source = input
  │     ├── 检查点 c2   模型想完、决定调工具之后      metadata.source = loop
  │     ├── 检查点 c3   工具执行完之后                metadata.source = loop
  │     ├── 检查点 c4   模型给出最终回答之后          metadata.source = loop
  │     └── 检查点 c5   运行结束后补写“耗时”标记      metadata.source = update（只改 metadata）
  │
  └── Run r2（用户发第 2 条消息）
        ├── 检查点 c6   parent = c5
        └── ……
```

读图时抓住三点：

1. **Thread 就是 LangGraph 的 `thread_id`**。检查点用 `(thread_id, checkpoint_ns, checkpoint_id)` 定位；DeerFlow 的主图是根图，所以源码里到处是 `"checkpoint_ns": ""`。
2. **Run 不是检查点的一部分**。Run 是 `runs` 表里的一行记录（见 [持久化与数据库](./12-持久化与数据库.md)）；它和检查点之间只有松散的关联：`ThreadDataMiddleware` 会把 `run_id` 盖在本轮最后一条人类消息的 `additional_kwargs` 上，运行结束后又会把“每个 run 花了几秒”记进检查点的 metadata（键名 `run_durations`）。
3. **检查点之间用 parent 指针串成一棵树**。线性对话时是一条链；“重新生成”“分支”会从旧检查点另起一条，链就变成了树（第 8 节）。

> **小贴士**：`metadata.source` 是 LangGraph 记在检查点里的“产生原因”。本章在源码里能直接看到的取值有：`input`（`runtime/goal.py` 的 `ensure_thread_checkpoint` 写空线程的根检查点时）、`loop`（测试夹具 `backend/tests/test_run_worker_rollback.py` 里模拟图执行步骤）、`update`（手工改状态时，如 `write_thread_goal`）、`branch`（`threads.py` 创建分支线程时）。

### 1.2 为什么多轮对话、刷新页面、中断恢复都离不开它们

**场景一：多轮对话。** Agent 的图本身像一个“没有记性的函数”。让它有记性的办法只有一个：启动之前，把 checkpointer 挂到图上，再在 config 里带上 `thread_id`。`run_agent` 就是这么做的：

> 来源：[`backend/packages/harness/deerflow/runtime/runs/worker.py`](../../backend/packages/harness/deerflow/runtime/runs/worker.py) → `run_agent`

```python
        # 4. Attach checkpointer and store
        if checkpointer is not None:
            agent.checkpointer = checkpointer
        if store is not None:
            agent.store = store
```

挂上之后，LangGraph 每次 `astream` 开始前会读出该线程的最新检查点，把这次的新输入用 reducer 合并进去（`messages` 追加一条人类消息），再往下跑；每跑完一步自动存档。所以“多轮”不是 DeerFlow 手写“把历史拼进提示词”，而是 LangGraph 的标准能力。

**场景二：刷新页面。** 浏览器里的 React 状态一刷新就没了。前端 `useStream` 带着 `fetchStateHistory: { limit: 1 }` 去后端要“最新一份状态”，对应 Gateway 的 `POST /api/threads/{thread_id}/history`；另外还有 `GET /api/threads/{thread_id}/state`。两条路由都通过 `CheckpointStateAccessor` 读检查点，把 `values`（也就是 `ThreadState` 的各个字段）原样返回。所以“刷新后还看得到历史”，本质就是**读最新存档**。

**场景三：中断与恢复。** 至少有三种情况要靠检查点：

- 用户“取消运行”：worker 在 `_finish_cancellation` 里分两种动作。动作是 `rollback` 时，把线程恢复到本次运行**之前**的检查点；否则运行状态记为 `interrupted`，线程停在**最后一个检查点**（本次已经干的活保留）。第 8 节细讲。
- 人机协作暂停：run 请求可以带 `interrupt_before` / `interrupt_after`，让图在某个节点前后暂停；`Command(resume=...)` 作为输入把暂停的图续上（`app/gateway/services.py` 里能看到 `graph_input = Command(resume=command["resume"])`）。暂停点保存在检查点里。
- 进程重启：只要 checkpointer 是 SQLite 或 Postgres，检查点就在磁盘 / 数据库里；如果是内存后端（`InMemorySaver`），重启即全部丢失。

| 你做的事 | 没有检查点会怎样 | DeerFlow 里谁在用检查点 |
| --- | --- | --- |
| 发第 2 条消息 | Agent 忘了第 1 条 | LangGraph 读档 + `messages` reducer 追加 |
| 刷新页面 | 聊天记录消失 | `GET /state`、`POST /history` 读最新检查点 |
| 点“重新生成” | 无处可退 | `regenerate/prepare` 找到“人类消息之前”的检查点，从那里重跑 |
| 点“停止并回滚” | 状态停在半截 | `_rollback_to_pre_run_checkpoint` 恢复运行前的状态 |
| 重启网关 | 所有会话归零 | 持久化的 checkpointer（SQLite / Postgres）重新读档 |

### 1.3 状态存在哪里：checkpointer，而不是内存变量

初学者容易把“线程状态”想成 Gateway 进程里的一个 Python 字典。**不是**。状态的唯一权威副本在 checkpointer 里；进程里的 `ThreadState` 只是“这一步图运行时的工作副本”。这有两个直接后果：

- **多个 Gateway 进程可以共享同一个线程**（只要它们共享同一个 Postgres 检查点库）——这也是第 6、7 节反复强调“各进程配置必须一致”的原因。
- **读状态要走“读档”流程**，而不是去翻某个全局变量——所以读写检查点必须经过统一入口 `CheckpointStateAccessor`（第 6.6 节）。

## 2. ThreadState：一块有 19 个格子的共享白板

### 2.1 它在源码里长什么样

`ThreadState` 定义在 [`backend/packages/harness/deerflow/agents/thread_state.py`](../../backend/packages/harness/deerflow/agents/thread_state.py)：

> 来源：[`backend/packages/harness/deerflow/agents/thread_state.py`](../../backend/packages/harness/deerflow/agents/thread_state.py) → `ThreadState`

```python
class ThreadState(AgentState):
    sandbox: SandboxStateField
    thread_data: NotRequired[ThreadDataState | None]
    title: NotRequired[str | None]
    artifacts: Annotated[list[str], merge_artifacts]
    todos: Annotated[list | None, merge_todos]
    goal: Annotated[GoalState | None, merge_goal]
    goal_outcome: NotRequired[GoalOutcomeState | None]
    uploaded_files: NotRequired[list[dict] | None]
    viewed_images: Annotated[dict[str, ViewedImageData], merge_viewed_images]  # image_path -> metadata (no base64)
    promoted: Annotated[PromotedTools | None, merge_promoted]
    delegations: Annotated[list[DelegationEntry], merge_delegations]
    skill_context: Annotated[list[SkillEntry], merge_skill_context]
    tool_artifacts: Annotated[list[ArtifactEntry], merge_tool_artifacts]
    tool_artifact_processed: Annotated[list[str], merge_artifacts]
    task_notes: Annotated[dict | None, TaskNotesChannel(dict | None, merge_task_notes)]
    task_history: NotRequired[dict | None]
    summary_text: NotRequired[str | None]
    background_tasks: NotRequired[list[BackgroundTaskState]]
```

**逐段解释**：

1. `class ThreadState(AgentState)`：继承 LangChain 的 `AgentState`，后者提供 `messages`（本章只确认这一个继承字段，LangChain 内部实现不展开）。`ThreadState` 自己再声明 **18 个字段**，所以白板一共 19 格。
2. **三种写法对应三种行为**：
   - `NotRequired[...]` 的**普通字段**（如 `title`）没有 reducer，同一步里有两个写入会冲突，没有写入则保持旧值，后一次写入直接覆盖前一次；
   - `Annotated[类型, reducer]` 是**带合并函数的字段**，多个写入会交给 reducer 合并（第 3 节）；
   - `sandbox: SandboxStateField` 是一个别名，等价于 `Annotated[NotRequired[SandboxState | None], merge_sandbox]`；`task_notes` 则是把一个**自定义通道对象** `TaskNotesChannel(...)` 放进了 `Annotated`（第 3.5 节）。
3. 行尾注释 `# image_path -> metadata (no base64)` 点出一个设计：图片字节不进检查点，只存元数据（`ViewedImageData` 的文档字符串里引用了 issue #4138：把 base64 重复写进每一份检查点太浪费）。
4. **数一数**：截至提交 `8d994cc1`，18 个自有字段里 **11 个带 reducer**（`sandbox`、`artifacts`、`todos`、`goal`、`viewed_images`、`promoted`、`delegations`、`skill_context`、`tool_artifacts`、`tool_artifact_processed`、`task_notes`），**7 个是普通覆盖字段**（`thread_data`、`title`、`goal_outcome`、`uploaded_files`、`task_history`、`summary_text`、`background_tasks`）。再加上继承来的 `messages`，同文件里的 `THREAD_STATE_REDUCER_FIELDS` 列了 **12 个**“合并型通道”。

> **注意**：`backend/packages/harness/deerflow/agents/AGENTS.md` 里的 ThreadState 字段清单已经过期（没有 `goal_outcome`、`tool_artifacts`、`tool_artifact_processed`、`task_notes`、`task_history`、`background_tasks`）。**以 `thread_state.py` 为准**。

### 2.2 字段全对照表

下表的“谁写 / 谁读”来自对源码的逐个检索（例子，不穷尽所有读者）。类型一栏为避免与表格分隔符冲突，把 `X | None` 写成“X（可空）”。

| 字段 | 类型 | reducer | 谁写 | 谁读 | 用途 |
| --- | --- | --- | --- | --- | --- |
| `messages` | `list[AnyMessage]`，继承自 `AgentState`；`delta` 模式下换成 `DeltaChannel` | 追加 / 按 id 更新（等价 `add_messages`；`delta` 模式用 `merge_message_writes`） | 几乎所有环节：用户输入、模型、工具、`ThreadDataMiddleware`、摘要中间件 | 模型调用、所有中间件、前端 | 对话历史本体 |
| `sandbox` | `SandboxState`（只含 `sandbox_id`，可空） | `merge_sandbox`：只接受幂等写入 | `SandboxMiddleware`（换 id 时用 `Overwrite`）与沙箱工具的懒初始化 | 沙箱工具、`ViewImageMiddleware`、`task_tool` | 本线程绑定的沙箱 id |
| `thread_data` | `ThreadDataState`（`workspace_path` / `uploads_path` / `outputs_path`，可空） | 无 | `ThreadDataMiddleware.before_agent` | `present_file_tool`、`ToolOutputBudgetMiddleware`、`ViewImageMiddleware`、`task_tool` | 本线程在磁盘上的三个目录 |
| `title` | `str`（可空） | 无 | `TitleMiddleware`（首轮之后）；`POST /state` 手工改名；重新生成时作为输入回放 | 前端（`AgentThreadState.title`） | 线程标题 |
| `artifacts` | `list[str]` | `merge_artifacts`：去重保序 | `present_file_tool`、`review_skill_package_tool` | 前端“产出物”面板 | 展示给用户的文件虚拟路径 |
| `todos` | `list`（可空） | `merge_todos`：后写胜出，`None` 表示没碰 | `write_todos` 工具（LangChain `TodoListMiddleware` 提供） | `TodoMiddleware`、前端待办面板 | 计划模式下的待办清单 |
| `goal` | `GoalState`（可空） | `merge_goal`：后写胜出，`None` 表示没碰 | Gateway 的 `PUT/DELETE /api/threads/{id}/goal`（经 `write_thread_goal`）；worker 的定时目标 | worker 的目标评估、`DurableContextMiddleware`、前端 | 线程级“持续目标” |
| `goal_outcome` | `GoalOutcomeState`（可空） | 无 | `write_thread_goal`（清除已达成的目标时带上结果）；重放时 worker 置 `None` | 前端（`ThreadGoalOutcome`） | 目标达成记录 |
| `uploaded_files` | `list[dict]`（可空） | 无 | `UploadsMiddleware`（每轮重新计算） | `list_uploaded_files_tool`、`TitleMiddleware`、`task_tool` | 本轮可见的上传文件 |
| `viewed_images` | `dict[str, ViewedImageData]` | `merge_viewed_images`：`{}` 清空，重复查看的移到末尾 | `view_image_tool` | `ViewImageMiddleware`（注入图片后清空） | 已查看图片的元数据（不含 base64） |
| `promoted` | `PromotedTools`（可空） | `merge_promoted`：按 `catalog_hash` 分域 | `tool_search`、`McpRoutingMiddleware`（经 `SkillToolPolicyMiddleware` 过滤） | `DeferredToolFilterMiddleware`、`DeferredToolPromotionAuditMiddleware` | 已“提拔”进模型视野的延迟工具名 |
| `delegations` | `list[DelegationEntry]` | `merge_delegations`：按 `(run_id, id)` 更新，终态不降级，最多 50 条 | `DurableContextMiddleware`（`before_model` / `after_model` 捕获 `task` 调用） | `DurableContextMiddleware._inject` | 子智能体委派账本 |
| `skill_context` | `list[SkillEntry]` | `merge_skill_context`：按 `path` 去重，最多 8 条 | `DurableContextMiddleware._capture`（识别读取 `SKILL.md` 的调用） | `_inject`、`SkillActivationMiddleware`、`SkillToolPolicyMiddleware` | 已加载技能的“引用”（路径 + 简述） |
| `tool_artifacts` | `list[ArtifactEntry]` | `merge_tool_artifacts`：按 `handle` 更新，上限 1000 | `ArtifactCaptureMiddleware` | `ArtifactResolutionMiddleware`、`DurableContextMiddleware` | 工具结果产物的“句柄 → 真实引用”登记表 |
| `tool_artifact_processed` | `list[str]` | `merge_artifacts`（复用）：去重保序 | `ArtifactCaptureMiddleware` | `ArtifactCaptureMiddleware`（跳过已处理项） | 已处理过的工具结果 / 调用的哈希键，防重复登记 |
| `task_notes` | `dict`（可空） | `TaskNotesChannel` + `merge_task_notes`：最多 8 条，每条最多 750 字符 | `task_note` 工具 | `DurableContextMiddleware`（开启任务连续性时） | 模型自己记的“任务笔记” |
| `task_history` | `dict`（可空） | 无 | 摘要中间件 / 上下文压缩 | `DurableContextMiddleware` | 被压缩掉的历史的归档引用 |
| `summary_text` | `str`（可空） | 无 | `SummarizationMiddleware._maybe_summarize`、手动 `compact` | `DurableContextMiddleware`、`PiiRedactionMiddleware`、`subagents/context_snapshot.py`、`client.py` | 摘要正文（第 4.2 节） |
| `background_tasks` | `list[BackgroundTaskState]` | 无 | `run_agent`（把 `mcp_tasks` 表投影进 `graph_input`） | 模型侧视图 | MCP 后台任务的摘要 |

**为什么要把这么多东西塞进“状态”，而不是各存各的？** 因为状态里的东西都要满足同一个条件：**它必须跟着检查点走**。读档 / 回滚 / 分支时，这 19 格会一起回到某个历史时刻，保证“待办清单、产出文件、沙箱 id”和“聊天记录”是同一时刻的一致快照；要是各存各的，回滚之后就会出现“聊天记录退回去了、产出文件还在”的错位。

### 2.3 前端能“看到”哪几格

前端 `AgentThreadState` 的类型声明只列了 7 个字段：

> 来源：[`frontend/src/core/threads/types.ts`](../../frontend/src/core/threads/types.ts) → `AgentThreadState`

```typescript
export interface AgentThreadState extends Record<string, unknown> {
  title: string;
  messages: Message[];
  artifacts?: string[];
  todos?: Todo[];
  goal?: GoalState | null;
  goal_outcome?: ThreadGoalOutcome | null;
  tool_artifacts?: ArtifactEntry[];
}
```

**逐段解释**：

1. `extends Record<string, unknown>` 表示“除了列出的 7 个，还可以有别的键”：后端返回的 `values` 里有 `sandbox`、`delegations` 等字段时，前端照样收得到，只是没有 TypeScript 类型提示。
2. 这 7 个字段是**界面确实要渲染**的：标题、消息、产出文件、待办、目标、目标结果、工具产物。
3. 契约文件 `contracts/thread_goal_contract.json` 固定了 `goal` / `goal_outcome` 的键，前后端靠它对齐。

> **注意**：把一个新字段加进后端 `ThreadState` **不会**自动出现在前端类型里；是否要改 `AgentThreadState`，取决于界面要不要用它（本章末尾“给未来 Committer 的话”会列出完整步骤）。

## 3. Reducer：为什么不能“后写覆盖前写”

### 3.1 三个现实问题

LangGraph 的规则是：**同一个超步（superstep，一批可以并行跑的节点）里，如果有多个写入落到同一个没有 reducer 的字段，会报错或丢数据**；有了 reducer，就把“多个写入怎么合并”变成一个你自己定义的函数。DeerFlow 的状态字段几乎都碰到了下面三类现实问题：

**问题 1：并行工具调用。** 模型一次返回多个 `tool_calls`，LangGraph 在同一个超步里并行执行它们。如果两个工具都要写 `artifacts`（比如同时 `present_files` 两个文件），没有 reducer 就是“两个写入抢一个格子”。源码里有两处直接的证据：`present_file_tool` 的文档字符串写着“This tool can be safely called in parallel with other tools. State updates are handled by a reducer to prevent conflicts.”；测试 `test_sandbox_field_is_wired_to_merge_sandbox` 的文档字符串写着：没有这个 `Annotated` 绑定，并发的沙箱工具持久化同一个懒初始化的 `sandbox_id` 时，会触发 LangGraph 的 `INVALID_CONCURRENT_GRAPH_UPDATE` 错误。

**问题 2：子智能体回写。** 主智能体用 `task` 工具派出多个子智能体；同一次委派会先后留下“进行中”和“已完成”两个版本，还可能带着相同的调用 id 重复出现（供应商的 tool-call id 在同一线程的后续运行里可能重复）。覆盖会丢记录，追加会重复，需要“按 key 更新、终态不降级”的合并（`merge_delegations`）。

**问题 3：中间件被反复执行。** `DurableContextMiddleware`、`ArtifactCaptureMiddleware` 这类中间件在**每次模型调用前**都会重新扫描整段消息历史来“捕获”东西，每次产出的更新里有大量旧内容。如果字段是“追加”，会越追越多；所以要“幂等”：同一个 key 只留一份，已处理过的用哈希键标记（`tool_artifact_processed`）。

### 3.2 全部 reducer 速览

| reducer | 套路 | 一句话规则 | 保护措施 |
| --- | --- | --- | --- |
| `merge_sandbox` | 幂等或报错 | 同一个 `sandbox_id` 的重复写入当作一次；不同 id 抛 `ValueError` | 换 id 要用 `Overwrite`（第 3.4 节） |
| `merge_artifacts` | 去重保序 | 旧列表 + 新列表，用 `dict.fromkeys` 去重、保持首次出现的顺序 | `tool_artifact_processed` 也复用它 |
| `merge_todos` | 后写胜出 | 新值非 `None` 就整体替换，`None` 表示节点没碰这个字段 | 空列表 `[]` 是一次明确的“清空” |
| `merge_goal` | 后写胜出 | 同上 | `None` 的清除要靠 `Overwrite(None)` 或 `write_thread_goal` |
| `merge_viewed_images` | 按 key 合并 | 新键覆盖旧键，**被更新的键移到末尾**（代表“最新”） | 新值是 `{}` 表示清空全部 |
| `merge_promoted` | 分域合并 | `catalog_hash` 相同则名字取并集；不同则整体替换 | 目录漂移后，旧名字不会误指向另一个工具 |
| `merge_delegations` | 按 key 更新 + 单调 | 以 `(run_id, id)` 为 key，同 key 取最新版；终态不被非终态覆盖 | 最多 50 条（`_DELEGATION_LEDGER_MAX_ENTRIES`），保留最新的 |
| `merge_skill_context` | 去重 + 刷新新旧 | 按 `path` 去重，再次读取会刷新“最近”位置 | 最多 8 条；描述最长 500 字符 |
| `merge_tool_artifacts` | 按 key 更新 + 滑窗 | 以 `handle` 为 key；带 `trim_to` 指令时按窗口淘汰最旧项 | 绝对上限 1000 条（`_ARTIFACT_MAX_ENTRIES_CEILING`） |
| `merge_task_notes`（经 `TaskNotesChannel`） | 校验后合并 | 值为 `None` 表示删除该 key；非法条目被丢弃 | 最多 8 条，每条最多 750 字符 |
| `merge_message_writes`（仅 `delta` 模式） | 线性时间的 `add_messages` | 按 id 追加 / 替换 / 删除；`REMOVE_ALL_MESSAGES` 清空 | 与公共 `add_messages` 语义一致 |

### 3.3 先看最简单的一个：`merge_sandbox`

沙箱 id 的规则最“严厉”：它**宁可报错也不乱选**。

> 来源：[`backend/packages/harness/deerflow/agents/thread_state.py`](../../backend/packages/harness/deerflow/agents/thread_state.py) → `merge_sandbox`

```python
def merge_sandbox(existing: SandboxState | None, new: SandboxState | None) -> SandboxState | None:
    """Reducer for sandbox state - accepts idempotent writes only.

    Multiple sandbox tools can initialize lazily in the same graph step and
    emit the same sandbox_id via Command(update=...). LangGraph needs an
    explicit reducer for that shared state key. Different sandbox ids in the
    same thread indicate a lifecycle/isolation bug, so fail closed instead of
    choosing one silently.
    """
    if new is None:
        return existing
    if existing is None:
        return new

    existing_id = existing.get("sandbox_id")
    new_id = new.get("sandbox_id")
    if existing_id == new_id:
        return existing
    raise ValueError(f"Conflicting sandbox state updates: {existing_id!r} != {new_id!r}")
```

**逐段解释**：

1. **场景**：模型一次调用了 `bash` 和 `read_file` 两个沙箱工具，它们都还没有沙箱，都会“懒初始化”一个沙箱并把同一个 `sandbox_id` 写回状态。两个写入内容相同，所以 reducer 直接返回 `existing`，不算冲突。
2. **`new is None` / `existing is None`**：没有新写入就保持旧值；第一次写入就接受新值。
3. **id 不一致就抛 `ValueError`**：同一线程里出现两个不同的沙箱 id，意味着沙箱生命周期或隔离出了 bug。这里选择**fail closed（失败即关闭）**——让这一步失败，也不悄悄选一个。这是 DeerFlow 反复出现的设计取向（见 [关键设计思想](../02-全局架构篇/05-关键设计思想.md)）。
4. 那线程**合法地**换沙箱怎么办（旧沙箱被回收了，要换新的）？走 `Overwrite`，下一节讲。

### 3.4 绕开 reducer 的“替换写”：`Overwrite`

reducer 管的是“合并”。但有些场景你要的是**替换**：把一个已经聚合好的值原样写回去，不要再合并一遍。LangGraph 为此提供了 `Overwrite` 标记：包在值外面，表示“跳过 reducer，直接用它替换”。DeerFlow 里有四处典型用法：

1. **沙箱换 id**：`SandboxMiddleware.before_agent` 发现线程之前的 `sandbox_id` 已经失效，要换成新的时，不能走 `merge_sandbox`（id 不同会抛错）：

   > 来源：[`backend/packages/harness/deerflow/sandbox/middleware.py`](../../backend/packages/harness/deerflow/sandbox/middleware.py) → `SandboxMiddleware.before_agent`

   ```python
               if existing_sandbox_id is not None:
                   return {
                       "sandbox": Overwrite({"sandbox_id": sandbox_id}),
                   }
               return {"sandbox": {"sandbox_id": sandbox_id}}
   ```

   旧 id 存在才用 `Overwrite`；第一次写入用普通字典即可。
2. **整体状态替换**（回滚、delta 线性化、分支复制）：`worker.py` 的 `_complete_state_replacement_values` 里有一行 `replacement_values[field_name] = Overwrite(replacement) if field_name in reducer_fields else replacement`。
3. **Gateway 的 `POST /api/threads/{id}/state`**：把客户端传来的值按“替换”写进去，同样用 `graph_reducer_channels` 判断哪些字段要包 `Overwrite`；创建分支（`/branches`）复制状态时也是——源码注释写得很直白：“reducer channels must not re-merge an already-aggregated value”。
4. **重放目标**：`worker.py` 里 `graph_input["goal"] = Overwrite(copy.deepcopy(current_values.get("goal")))`，因为 `merge_goal` 会忽略普通 `None`。

`Overwrite` 有两个容易踩的坑：

- **读的人要拆包**。回滚恢复（delta 模式）可能把 `sandbox` 通道以 `Overwrite(...)` 的形态原样交到读者手里，所以 `sandbox/overwrite.py` 提供了 `unwrap_sandbox`，沙箱工具和中间件读 `state["sandbox"]` 前都要先拆包（它还会告诉你“这是不是 fork 恢复来的”，是的话不要当成本次运行拥有的沙箱去释放）。
- **LangGraph 自己有个小 bug**：往一个“还是空的”（MISSING）reducer 通道里**第一次**写 `Overwrite` 时，通道会把 `Overwrite` 包装对象原样存起来（上游问题，仓库内编号 #4380）。`backend/packages/harness/deerflow/checkpoint_patches.py` 在 import 时打了一个兼容补丁，并且带“探测”逻辑：上游修好了就自动停用。这个补丁挂在 `thread_state.py` 的 import 上，保证网关、worker、测试进程都带着它。

### 3.5 自定义通道：`TaskNotesChannel`

有一个字段连 reducer 都嫌不够：`task_notes`。它用的是一个自定义通道类：

> 来源：[`backend/packages/harness/deerflow/agents/task_continuity/state.py`](../../backend/packages/harness/deerflow/agents/task_continuity/state.py) → `TaskNotesChannel`

```python
class TaskNotesChannel(BinaryOperatorAggregate[dict | None]):
    """Validate every checkpoint write, including first writes and Overwrite.

    Keep the optional channel uninitialized until it receives a write so the
    disabled feature does not add a notebook to ordinary state/SSE snapshots.
    """

    def update(self, values: Sequence[dict | None]) -> bool:
        changed = super().update(values)
        if changed:
            self.value = normalize_task_notes(self.value)
        return changed
```

**逐段解释**：

1. `BinaryOperatorAggregate` 是 LangGraph 里“用二元函数合并写入”的通道，普通 reducer 字段背后就是它。
2. 这里**重写 `update`**，在每次更新之后再跑一遍 `normalize_task_notes`。原因写在文档字符串里：reducer 管不到“首次写入”和 `Overwrite`——它们可以绕过 `merge_task_notes` 把脏数据写进来；而笔记是**模型自己写的、不可信的内容**，每一次落盘都必须校验（键名格式、长度、来源 id 格式、条数）。
3. 第二句话：通道在收到第一次写入之前保持“未初始化”，所以**没开启这个功能的线程，状态快照里根本没有 `task_notes`**，不会多出一个空笔记本。

## 4. messages 怎么长大，又怎么被“压缩”

### 4.1 追加与按 id 更新

`messages` 的合并语义在两种模式下一致：**新消息追加到末尾；id 相同的消息原地替换；`RemoveMessage` 删除指定 id；`REMOVE_ALL_MESSAGES` 清空它之前的所有内容**。`delta` 模式下由 `merge_message_writes` 实现，它的文档字符串说明了目标：以线性时间复现公共 `add_messages` 的全部行为（强制转换、id、删除、`REMOVE_ALL_MESSAGES`）。

两个细节直接影响你读代码：

- 没有 id 的消息会被补一个 `uuid4`（`_normalize_messages`），所以**图里流转的每条消息都有 id**。
- 因为“同 id 即替换”，中间件可以通过返回 `"messages": [...]` 来**原地修改**一条已有消息。`ThreadDataMiddleware` 就是这样给本轮最后一条人类消息盖上 `run_id` 和时间戳的：它把 `last_message.model_copy(update=...)` 放回列表，id 没变，所以不是“追加”而是“替换”。

清空分支很短，值得看一眼：

> 来源：[`backend/packages/harness/deerflow/agents/thread_state.py`](../../backend/packages/harness/deerflow/agents/thread_state.py) → `merge_message_writes`

```python
        if remove_all_idx is not None:
            messages = list(normalized_write[remove_all_idx + 1 :])
            latest_position, positions_by_id = _index_messages(messages)
            continue
```

意思是：如果这一批写入里出现了 `REMOVE_ALL_MESSAGES`，就**丢掉此前累计的全部消息**，只保留这个标记**之后**的那些，然后重建索引继续处理后面的写入。下一小节的摘要就是靠它实现的。

### 4.2 摘要之后：`REMOVE_ALL_MESSAGES` + `summary_text`

对话太长，上下文放不下了怎么办？`SummarizationMiddleware`（[中间件链](./04-中间件链.md) 里的一员）会把旧消息总结成一段文字。关键看它**往状态里写了什么**：

> 来源：[`backend/packages/harness/deerflow/agents/middlewares/summarization_middleware.py`](../../backend/packages/harness/deerflow/agents/middlewares/summarization_middleware.py) → `SummarizationMiddleware._maybe_summarize`

```python
    def _maybe_summarize(self, state: AgentState, runtime: Runtime) -> dict | None:
        result = self.compact_state(state, runtime, force=False)
        if result is None:
            return None
        return {
            "messages": [
                RemoveMessage(id=REMOVE_ALL_MESSAGES),
                *result.preserved_messages,
            ],
            "summary_text": result.summary_text,
            **({"task_history": result.task_history} if result.task_history is not None else {}),
        }
```

**逐段解释**：

1. `RemoveMessage(id=REMOVE_ALL_MESSAGES)` 加上 `*result.preserved_messages`：**把整段历史替换成“需要保留的那几条”**（系统消息、带标签的动态上下文提醒、当前用户请求等，保留规则见 `_preserve_required_context`）。
2. **摘要正文不是一条消息**，而是写进独立字段 `summary_text`。
3. `task_history` 只有在开启“任务连续性”配置时才写（`result.task_history is not None`），用展开式 `**({...} if ... else {})` 条件加入字典。
4. 模型怎么看到摘要？`DurableContextMiddleware` 在**每次模型调用时**把 `summary_text`（连同 `delegations`、`skill_context`、`tool_artifacts` 等）渲染成一条隐藏的 `<durable_context_data>` 人类消息塞进请求里，**不写回状态**（该文件的模块文档字符串写明：never written back to state）。

> **为什么这样设计**：摘要放在 `messages` 之外有三个好处。①它不会被下一次压缩当成“普通消息”再摘要一遍而越缩越失真；②渲染时可以统一做长度预算（`_SUMMARY_RENDER_CHAR_BUDGET`）和敏感信息脱敏（`redact_text`）；③摘要被标为**不可信数据**，渲染时和“用户指令”分开放置，降低提示词注入风险（模块文档字符串里写明：`summary_text`、`delegations`、`skill_context`、`tool_artifacts` stay untrusted data）。

### 4.3 摘要不会碰的那些通道

压缩只改 `messages`、`summary_text`、（可选）`task_history`。其它 16 格**原封不动**，这正是 `delegations`、`skill_context`、`tool_artifacts` 这些字段存在的理由——**让重要信息不依赖聊天记录里那几条消息**：

- `ArtifactEntry` 的文档字符串：登记在 `ThreadState.tool_artifacts` 里，“so it survives context compaction”；模型只看到短 `handle`，真实路径 / URL 在状态里，调用工具时再解析。
- `merge_skill_context` 的文档字符串：`loaded_at` “is observational only because message indices reset after compaction”——压缩后消息下标会重置，所以排序不能依赖它。
- 手动压缩接口 `POST /api/threads/{id}/compact` 只写 `messages` 和 `summary_text`，其它通道靠“检查点 fork 继承”自动带过去（路由里的注释这样写）。
